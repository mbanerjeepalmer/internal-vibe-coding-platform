Hit and fixed a real Workers-runtime incompatibility, found only by actually deploying and calling the live endpoint (not something visible from a local build): `@daytona/sdk` talks to Daytona's API through axios, whose fetch adapter always constructs its own `Request` object with `cache: 'default'` baked in (`new Request(url, { cache: 'default', ... })`) before calling `fetch(thatRequest)`. Cloudflare Workers' `fetch` rejects any `Request` built with an explicit `cache` value at all — `DaytonaError: Unsupported cache mode: default` — even though `'default'` is nominally the spec default; the point is that Workers only tolerates the field being *absent*, not merely resolving to the default value. First attempted a `fetch()` patch stripping `init.cache`, which did nothing — the cache mode is already baked into the `Request` object passed as `fetch`'s first argument by that point, not read from the second argument. Fixed by patching the global `Request` **constructor** instead (`src/lib/server/opencode/sandbox.ts`, `patchFetchForWorkersCacheBug`) — wraps `globalThis.Request` in a `Proxy` that strips `cache` from `init` before delegating to the real constructor. Applied once, lazily, right before the Daytona client is created; harmless on Node (verified `npm run dev`/local provider still works unaffected).

Verified the fix live end-to-end against the deployed Worker itself, not just locally: `/api/kitchen/.../models` (real Daytona sandbox creation + opencode install from inside a Workers isolate), a full prompt -> SSE event stream round trip via curl, and a full Playwright browser run against `/live` on the live URL (real cold sandbox provisioning, ~3 min first-time, then a working chat turn rendered in the browser).
